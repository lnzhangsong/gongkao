# 读本 READBOOK · 产品埋点设计方案（PostHog）

> 状态：**已实施**（E1 基础接入 + E2 功能事件；E3 分析面板待建）
> 起草日期：2026-09-07 ｜ 实施日期：2026-09-07
> 背景：项目尚无真实用户，需要在推广前先能回答「有没有人用、从哪来、用哪些功能、在哪一步流失」。经方案比选（Vercel Analytics / Umami / GA4 / 百度统计 / Plausible / PostHog / 自建），**用户已裁定选 PostHog 云**。
> 原则：**不采集任何个人身份信息**（不传邮箱/昵称/正文内容/笔记内容）；埋点失败绝不影响主功能。
>
> 实施结果：埋点全部由 `src/lib/analytics.ts` 封装 PostHog 云（美区）承载。此前一度落地的自建 Supabase `app_events` **写入逻辑已整体下线**（全仓已无任何读写代码；历史上该表的唯一写入者就是 `analytics.ts`）。云端表本身**尚未删除**——需手动重跑 `sql/sync.sql` 的 `drop table`，见 §五 第 1 步。

## 一、要回答的问题（埋点的验收标准）

| # | 问题 | 需要的数据 |
|---|---|---|
| Q1 | 有没有人来？从哪来？ | PV/UV、referrer、设备 |
| Q2 | 来了用不用？用哪块？ | 各页面停留与功能事件计数（阅读/摘录/申论/真题/ASSIST） |
| Q3 | 账号链路通不通？ | 注册/登录/退出计数、同步成功率 |
| Q4 | AI 功能有没有人真的在用？ | 各 AI 动作的触发次数与成功率 |
| Q5 | （后续）答题卡落地后的转化 | 「打开题目 → 写答案 → 完成」漏斗 |

Q1-Q2 靠自动采集，Q3-Q5 靠一组人工埋点事件（下文 §三）。

## 二、接入设计

### 2.1 技术形态

- 依赖：`posthog-js`（官方前端 SDK，完整构建约 278KB / gzip 92KB，独立 chunk 懒加载不阻塞首屏）
  - 原方案按「~20KB gzip」估算，实测偏大 4 倍有余：`posthog-js` 主入口把功能开关、问卷、
    Toolbar 等一并打包，即便这些扩展已关闭也仍在产物里。因该 chunk 完全不在首屏关键路径，
    暂不为省体积去换未公开的 slim 子路径（且换后需重新验证 history pageview 采集）
- 初始化：`src/lib/analytics.ts` 封装，`main.tsx` 调 `initAnalytics()`——用 `requestIdleCallback`
  （老浏览器回退 `setTimeout`）把 SDK 的**动态 import + init** 推到空闲时段。
  初始化必须早于首次路由跳转：SDK 负责上报 pageview，只在白名单事件触发时才加载就会漏掉
  「纯浏览、没触发任何功能事件」的访客，Q1 直接失真
- 实际下发的关键配置：`capture_pageview: 'history_change'`、`capture_pageleave: true`、
  `autocapture: false`、`disable_session_recording: true`、`capture_exceptions: false`、
  `person_profiles: 'identified_only'`
  - **autocapture 关闭**：全量 DOM 自动采集噪声大且可能带敏感文本，只走白名单事件
  - **会话回放/异常采集关闭**：本期只做 Product analytics，回放会录屏、异常采集会带堆栈
  - **`person_profiles: 'identified_only'`**：未 identify 前不建 Person，省额度也少存匿名档案
  - SPA 路由 pageview：SDK 监听 history 变化自动上报，App 里不再手写 pageview（原先的
    `AnalyticsRoute` / `trackPageview` 已删除，否则会与 SDK 重复计数）
- 未配置 `VITE_POSTHOG_KEY` 时**整个模块静默失效**：本地开发与 CI 无需真实 key，也不会报错。
  构建期 Vite 会把该变量常量折叠成 `undefined`，压缩器据此判定 `loadClient()` 必然提前返回，
  于是 `import('posthog-js')` 被整体消除——**产物里连 chunk 都不会出现，零字节开销**
  （已实测：不带 key 构建时 `dist/` 中不含 posthog；带 key 时独立 chunk ≈ 278KB / gzip 92KB，
  主 chunk 只增 ~5KB 的封装代码）
- **国内访问与去广告拦截：反向代理（关键项）**
  - 默认 SDK 直连 `us.i.posthog.com`，国内直连慢且易被广告插件拦
  - 方案：SDK 的 `api_host` 设为 `/ingest`，请求先落到自身域名再反代出去
    - 生产：`vercel.json` 两条 rewrite —— `/ingest/static/(.*)` → `us-assets.i.posthog.com/static/$1`，
      `/ingest/(.*)` → `us.i.posthog.com/$1`（**静态资源走 assets 域，且必须排在通配前**）
    - 本地：`vite.config.ts` 的 `server.proxy` 配同样两条，开发环境行为与线上一致
  - 走自己域名（同站、同 CDN），既绕广告拦截又无新增被墙面
  - Service Worker 显式放行 `/ingest/`（与 `/api/` 同规格）：埋点是跨域转发的 POST/beacon，
    经 SW 兜一圈没有收益，还可能让 `sendBeacon` 在页面卸载时被延迟
- `ui_host` 固定为 `https://us.posthog.com`：仅用于 Toolbar 等回跳 App 的链接，与上报无关

### 2.2 身份策略

- **匿名优先**：不调 `identify`，所有事件挂在 PostHog 匿名 id（cookie/localStorage）上
- 登录后调 `posthog.identify(<supabase user id>)`——只有一串无意义的 uuid，**不传邮箱/昵称**；这样能区分「匿名浏览」与「注册用户」两条曲线，且同设备先匿名后登录能归并为同一个用户
- 退出登录（`authStore.signOut`）调 `posthog.reset()`：解除身份关联并换一个匿名 id，
  否则退出后的事件会继续记在上一个账号名下
- `identify` 必须排在 `track('auth_login')` **之前**：两者挂在同一个「SDK 就绪」Promise 上按注册顺序执行，顺序反了登录事件就会落在匿名 id 上
- 不采集：文章正文、摘录/笔记内容、AI prompt 与生成全文、API key（当然）。事件 props 只允许 id 类（articleId/paperId）、枚举类（题型/主题/成败）与数值（字数等）

## 三、事件清单（白名单，先少后多）

| 事件 | 触发点 | props | 状态 |
|---|---|---|---|
| `pageview` | SDK 自动（history 变化） | — | ✅ |
| `auth_login` | 登录成功（`authStore.onSignedIn`） | provider: password/magic_link/… | ✅ |
| `auth_logout` | 退出确认（`authStore.signOut`） | — | ✅ |
| `sync_done` | 云同步**完整轮次**结束（`cloudSync.runSyncInner`） | duration_ms | ✅ |
| `sync_error` | 同上，出错时 | table, duration_ms | ✅ |
| `article_read_finish` | 进度达 95%（`articleStore.saveProgress` 首次完成） | articleId, topic | ✅ |
| `annotation_add` | 新增高亮/下划线/笔记（`annotationStore.add`） | kind, articleId | ✅ |
| `shenlun_deconstruct` | 拆解保存（`shenlunStore.upsert` 出现实质加工内容） | articleId | ✅ |
| `exam_trace` | M1 思路推导保存（`examStudyStore.setPoints` / `addPoint`） | paperId, qIdx, origin | ✅ |
| `assist_generate` | AI 审题框架/完整出题**成功**后 | mode: framework/full_exam, questionType | ✅ |
| `answer_write` / `answer_check` | 答题卡 P1/P3 落地后接入（预留） | paperId, qIdx | ⏳ 预留 |

埋点点位多数是**现有动作处加一行**；`article_read_finish`、`exam_trace`、`assist_generate` 的触发位置在 store/页面里都已存在，无需新逻辑。

实施时的两处收敛（与草案的差异）：

- **`sync_done` / `sync_error` 只埋完整轮次**（登录首轮 / 窗口聚焦 / 手动同步），不埋编辑触发的
  轻量 push 轮次——push 有 4s 防抖，边写边同步会刷出大量几乎无信息量的事件
- **`sync_error` 只报出错的表名与耗时，不报错误正文**：Supabase 的错误串可能带上账号/权限细节，
  与「不传 PII」冲突
- `assist_generate` 从「调用前上报」改为「**成功后**上报」：草案要求该事件回答的是「有没有人真的在用」，
  只记尝试会把失败也算成使用量（失败另有 `alertDialog` 提示，不依赖埋点发现）

## 六、风险与回退

| 风险 | 缓解 |
|---|---|
| PostHog 云国内加载慢 | §2.1 反代走自己域名；SDK 懒加载，最坏情况埋点静默失败、主功能零影响 |
| 广告插件拦截 | 同上，反代同域后绝大多数拦截规则不再命中 |
| 免费额度政策变化 | 事件白名单克制；封装集中在 `analytics.ts`，换供应商（如 Umami）只改一个文件 |
| 隐私合规 | 不传 PII；文档明示；如需彻底自持数据，未来可平移 PostHog 自托管或 Umami |
