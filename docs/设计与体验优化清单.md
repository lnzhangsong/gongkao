**附：OpenUI 评估结论（2026-09-14，不实施）**

日后重提时可直接引用，不必重查：

- **它是什么**：openui.com = Thesys 的「生成式 UI 开放标准」——LLM 输出 OpenUI Lang（一门 DSL）→ 前端解析渲染成组件树。开源 MIT、可自托管，包 `@openuidev/lang-core`（dist 144K，运行时依赖仅 `ci-info`）、`react-lang`、`react-headless`、`react-ui`。注意与早年同名的 `wandb/openui` 不是一回事。
- **不引入的三条理由**：
  1. **语法不匹配**：位置参数适合「少而必填」的 UI 组件，不适合 `AnswerPointTrace`（8 字段、含多个可选字段，如 `sourceIdx` / `quote` / `note`）。
  2. **转义风险**：字段多为长中文散文与材料原文（`quote` 即原文连续片段），自定义 DSL 需自行定义转义规则，而 JSON 有标准转义。引入会新增「转义错 → 整条失败」的新故障类。
  3. **省不下 token**：实测同内容，压缩 JSON 261 字符 vs OpenUI Lang 235 字符，**仅 1.11 倍**（缩进 JSON 为 1.62 倍）。而 `draftMaterialMarks` 一次 30~60 条、`maxTokens: 8000`、界面标注「约需十几秒」——一旦校验失败回灌重试，重生成整份的代价远超本地归一化（`ROLE_ALIAS` 那套手写映射在这个量级上反而是**更经济**的解法）。
- **它真正无替代品的是流式**（前向引用 / 节点 `partial` / 增量解析 / `incomplete` 区分「没说完」与「说错了」）。本项目解析链路当前**不需要流式**，故触发条件不成立。**若将来要做「边生成边读要点」的流式解析，再重新评估**——那时它的发动机才对得上。
- **附带**：`@openuidev/lang-core` 的 postinstall 会发匿名安装遥测到 PostHog（哈希项目 ID / OS / 运行时版本 / 对方观测到的 IP，不含源码与 prompt），可用 `OPENUI_TELEMETRY_DISABLED=1` 关闭；pnpm 默认亦拦截 build script 不执行。
